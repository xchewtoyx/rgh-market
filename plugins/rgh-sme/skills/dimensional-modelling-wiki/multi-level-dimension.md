Most fact tables sit at one fixed grain relative to a dimension's hierarchy — sales transactions always reference an individual product, a sales plan always references a brand — and different levels are normally handled by giving each its own fact table with a correspondingly leveled dimension, one at the atomic grain and one built as a [shrunken (rollup) dimension](shrunken-dimension.md). That separation breaks down when a *single* business process genuinely produces events at varying levels of the same hierarchy — a web page-view event, for instance, might describe one specific product, or a whole category of products, or no product at all, depending on which page was viewed.

A **multi-level dimension** handles this by adding extra rows to the dimension, one per distinct higher-level value that events need to reference, alongside its normal atomic-grain rows — a product dimension gains additional rows representing each brand, category, and subcategory actually referenced by some event, on top of its ordinary one-row-per-product rows. Events with no product context at all use the dimension's ordinary [special-case "missing" row](special-case-dimension-row.md) (surrogate key `0`); events at a higher level use one of these new extra rows instead, each carrying its own distinct special-case-style surrogate key.

## Level Type

A multi-level dimension needs a **level type** attribute documenting what each row represents: ordinary rows default to the dimension's own name (an individual product, an individual employee), while the added rows are labeled after whichever hierarchy-level attribute they stand in for (category, subcategory, brand). This lets ETL manage the extra rows distinctly from ordinary members, lets a query constrain to a specific level when that's genuinely wanted, and can otherwise be ignored entirely by a query that just wants everything rolled up to one level — grouping by category, for example, automatically includes product-level, brand-level, subcategory-level, and category-level rows within the right category group with no extra logic needed.

A recurring discovery-time signal that a multi-level dimension is needed: stakeholders describing example events using values that are normally *higher* up the hierarchy than expected for that dimension (naming an organization when an individual was expected, or a product category when a specific product was expected).

## Optional bridge: combining with a bridge table for the rare split-detail query

A [bridge table](bridge-table.md) is the general answer whenever a fact row must relate to more than one member of a dimension at once (several employees jointly credited with one sale, say) — but building every query through a full bridge is excessive when most reporting only wants the group rolled up to a single level (a branch total) and only a minority of queries need the actual per-member split. A multi-level dimension paired with an **optional bridge table** covers both needs at once: add pseudo-member rows to the dimension for each group that actually occurs (a "Holmes & Watson" row alongside the ordinary individual-employee rows), let the fact table join directly to those pseudo-member rows for ordinary rollup reporting with no bridge involved, and reserve a separate bridge table — sharing the same surrogate keys as the multi-level dimension, so it stays a [swappable dimension](supertype-subtype-schema.md) relative to it — purely for the queries that need the individual split (a per-member percentage). A membership-type attribute on the bridge (distinguishing an ordinary single member, a genuine multi-member split row, and the group-level pseudo-member itself) lets one query return individual, group, and combined totals side by side, provided it filters on membership type to avoid double-counting a group's total alongside its own members' totals.

Multi-level dimensions add real flexibility but are easy to over-apply — reserve them for processes that genuinely mix levels, and keep an ordinary single-level version of the same dimension (with no level-type attribute at all) for every fact table whose grain is genuinely fixed, so the presence of a level-type attribute reliably signals "this fact table's dimensionality varies" rather than appearing everywhere out of habit.

**Never use a multi-level dimension to change what a fact means.** It is safe specifically because the fact stays additive and meaningful regardless of which level a given row happens to be at — page dwell time and page-view counts mean the same thing whether the row is at product or category level. It is not a substitute for combining genuinely different measurements at different grains: storing a brand-level planned target and a product-level actual sales figure in the same fact table remains wrong for the reasons described under [grain](grain.md) and [business process](business-process.md) even if a multi-level dimension is available, since planning and selling are different business processes with different facts, and mixing category-level summary rows into an otherwise product-level sales fact table makes the fact non-additive across level type — every query would then have to remember to constrain to one level or silently double-count, exactly the trap [aggregate fact table](aggregate-fact-table.md)s exist to avoid by staying in their own separate table.
