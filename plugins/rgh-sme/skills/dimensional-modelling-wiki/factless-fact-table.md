Some business events record only a set of dimensional entities coming together at a moment in time, with no numeric result to capture — for example, a student attending a class, with foreign keys for day, student, teacher, location, and class, but no fact column. This is a factless fact table; a dummy constant-value fact (e.g., a count of 1) is sometimes added as a cosmetic convenience so BI tools can count rows without arbitrarily picking a foreign key to aggregate on. SQL can already count rows without such a column — `COUNT(some_key)` counts keys "flying by" the query, not distinct values — but an explicit always-1 count column makes the SQL more readable, is easier for some BI tools to generate automatically, and is generally required to build a summarized [aggregate fact table](aggregate-fact-table.md) on top of the factless table (a real column is needed to `SUM` into a meaningful rollup count) or to deploy the table as an [olap-cube](olap-cube.md), where dimension join keys aren't explicitly exposed inside the cube the way they are in a relational join. Once this column is added the table is technically no longer factless, but it remains a factless table in spirit — the added column is administrative, not a measurement.

**Performance caveat**: adding the constant-1 fact so queries can use `SUM()` instead of `COUNT()` can backfire. A database optimizer evaluating `COUNT()` over an indexed column can sometimes satisfy the query from the index alone, without reading the underlying fact rows from disk at all; `SUM()` over a physical fact column forces the RDBMS to actually read every qualifying row to fetch its value first — extra disk I/O, worse when matching rows aren't clustered together, and more likely to bite under a star-join optimizer that applies dimensional constraints before touching the fact table. Not every optimizer behaves this way, and behavior may be tunable — worth checking with a DBA before assuming the constant-fact column is free. Adding the column doesn't preclude also writing plain `COUNT()` queries against the table; both remain valid.

## Coverage tables: analyzing what didn't happen

A factless fact table can also represent the universe of possible events rather than the events that occurred — a **coverage** (or event) fact table. For example, a sales [fact-table](fact-table.md) only records products that actually sold on promotion, and can't answer "what products were on promotion but did *not* sell?" A promotion coverage factless fact table, keyed by date, product, store, and promotion — structurally similar to the sales fact table but at a different [grain](grain.md): one row per product on promotion per store per day, regardless of whether it sold — supplies the universe of promoted products. Set-differencing the coverage table against the activity table (sales) then yields the events that did not happen. This requires two separate queries in a relational engine; [olap-cube](olap-cube.md)s, which contain explicit cells for non-behavior, often answer "what didn't happen" more directly.

A **condition** — an eligibility, coverage, or assignment relationship that holds over a point or period in time rather than at a transaction — is a related but distinct use of the factless design from the activity-counting case above (customer contacts, page views, attendance), even though both are structurally "just foreign keys." A salesperson-to-customer assignment, for instance, exists independently of whether that salesperson ever actually books an order from that customer — an order table's contents aren't a reliable stand-in for the assignment relationship, since an order can occur without an assignment (a customer buying from an unassigned rep) just as an assignment can exist with no resulting order. A factless condition table typically carries an effective and expired date-key pair per row (with a reserved far-future date key for a still-open condition, per [null handling in dimensional models](null-handling-in-dimensional-models.md)) rather than a single event date, and — unlike an activity factless table, which is often interesting on its own — is rarely studied alone: its value comes from comparing it against a companion activity table. A **factless snapshot**, recording one row per condition per period (month, quarter) rather than an exact effective/expired date range, is a coarser-grained alternative that trades precision for simpler SQL, following the same density trade-off as any other [periodic snapshot fact table](periodic-snapshot-fact-table.md).

### Comparing a condition table against an activity table

Finding the mismatch between a condition and an activity (e.g., "which assigned customers placed no orders last quarter," or its mirror, "which orders came from unassigned customers") takes one of a few forms, none of them reasonable to expect from an end user or most reporting tools directly:

- **Set difference (`MINUS`/`EXCEPT`)**: one query produces the qualifying dimension-pair keys from the condition table (e.g., salesperson/customer pairs with an assignment active during the target period), a second produces the same shape of keys from the activity table, and the difference between the two sets is the answer. Reversing the two queries answers the mirror question.
- **Numbered periods**: an effective/expired date-range overlap predicate is easy to get wrong; giving the date dimension a simple incrementing period-number column (quarter 1 = 1, quarter 2 = 2, ...) turns the overlap test into a plain integer range comparison. A factless snapshot sidesteps the same problem by making period membership a matter of row existence instead of a date-range test at all.
- **Correlated subquery (`NOT EXISTS`)**: the main query selects from the condition table, with a correlated subquery checking for a matching activity row per pair — correlate on **natural keys**, not surrogate keys, since either dimension may have undergone a [slowly changing dimension type 2](slowly-changing-dimension-type-2.md) change during the period being studied, and the two tables' surrogate keys for "the same" real-world pair won't reliably match. This form is harder to read than a set difference but is necessary when the result also needs columns that exist only in one of the two tables (e.g., summing an activity fact only for pairs matching a condition, via `EXISTS` instead of `NOT EXISTS`).

When none of these is fast enough or exposable to end users, a fourth option is to precompute the comparison at ETL time into its own dedicated star instead of at query time — a [set operation fact table](set-operation-fact-table.md), one instance of a [derived schema](derived-schema.md) built specifically to answer one recurring cross-table question.

Because a type 2 change to a dimension used in a condition table requires a new fact row (the same natural-key entity now has a new surrogate key, and the condition relationship must be re-expressed against it — mirroring how a [bridge table](bridge-table.md) must add rows when a bridged dimension changes), the natural-key correlated-subquery form above is the most robust of the three techniques under ordinary type 2 churn; a `MINUS`/`EXCEPT` query built against descriptive attributes rather than natural keys (customer or salesperson *names*, for instance) can silently break the moment one of those names changes under type 2.

### When explicit non-event rows can live in the activity table itself

A separate coverage table is the general-purpose answer, but it isn't the only one: explicit rows for the non-event case (an attendance metric of 0 alongside 1 for attendance, say) can instead be added directly into the *same* fact table that already records the events that did occur — no longer factless once that flag exists, but avoiding a second table and a set-difference query altogether. This inline approach is viable only when two conditions both hold: the non-event rows share the exact same dimensionality as the event rows (nothing extra needs to be modeled to describe a non-event), and the population of possible non-events is bounded enough that the table won't grow alarmingly (e.g., students registered for a course who didn't attend a given class session — a small share of registrants on any given day). The authors call this "ridiculous in many other situations" — inserting a row into a customer's sales-transaction fact table for every promoted product that customer *didn't* buy would explode the table for comparatively little analytic value; that's exactly the case the separate coverage-table pattern above exists for instead.
