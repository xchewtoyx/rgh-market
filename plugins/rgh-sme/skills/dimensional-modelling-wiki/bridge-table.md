Every dimension attached to a [fact-table](fact-table.md) is normally expected to take a single value per fact row, via one clean foreign key. Some dimensions are legitimately **multivalued** at the fact table's [grain](grain.md) — a healthcare patient with multiple simultaneous diagnoses, demographic descriptors sourced from multiple providers, a commercial customer with several points of contact, a job applicant with several skills (see [multivalued attribute query patterns](multivalued-attribute-query-patterns.md) for how to query "and"/"or" combinations of these), joint bank account holders (see [weighted vs. impact reports](weighted-vs-impact-reports.md) for how to report correctly when bridged members jointly share responsibility for the same facts), vehicle optional features. A bridge table attaches via a group dimension key on the fact row, and holds one row per simultaneous value in that group — rows exist only when needed, so the design scales to hundreds or thousands of values without the null bloat a positional design (one column per possible value) would create.

A quick discovery-time question surfaces most genuinely multivalued details: after establishing an ordinary example of an event detail, ask stakeholders directly for an example of the same event involving a *group* of that detail instead of one — most details won't have a plausible group example, which is exactly what confirms they're single-valued; the exceptions that do are the multivalued (and often [multi-level](multi-level-dimension.md)) candidates worth modeling with the techniques below.

**Before reaching for a bridge table, confirm the fact table is genuinely at its atomic [grain](grain.md).** An attribute that looks multivalued is sometimes only an artifact of a fact table sitting above its true atomic level — a header-grain invoice fact table can make product look multivalued (several products per invoice) purely because the table wasn't built at line-item grain in the first place. Rebuilding at the real atomic grain resolves that case directly and is simpler than a bridge; a bridge table is the right tool specifically for a dimension that is still genuinely multivalued once the fact table is already sitting at its true atomic grain.

## Fixed-role flattening vs. bridge table (multi-valued dimensions)

The bridge pattern above applies when a *dimension attribute* takes multiple simultaneous values. A related but distinct case is a **multi-valued dimension**: a fact row that must relate to more than one *row* of an entire dimension table at once — an order with several collaborating salespeople, rather than a customer with several skills. Two designs address this:

- **Fixed-role flattening**: decompose the many-to-many relationship into two or more one-to-many relationships using [role-playing dimension](role-playing-dimension.md)s — e.g. `order_facts` gets both a `primary_salesrep_key` and a `secondary_salesrep_key`, each aliasing the same salesrep table under a distinct role, with unused roles pointing at a "not applicable" row. This complicates reporting (finding "all orders involving a given salesperson" means filtering on every role column and combining the results) and supports only a fixed number of simultaneous values — a new record-holder breaks the design. It can still be the right choice when the multi-valued case is rare and bounded, letting most reporting use the primary role alone while trained analysts handle occasional multi-role reports.
- **Bridge table**: a group table sits between fact and dimension instead — a `group_key` on the fact row, and one bridge row per group member, all sharing that `group_key`. The fact-to-bridge relationship is genuinely many-to-many by design (the same `group_key` recurs across many fact rows, and can recur again if the same group collaborates again), which can confuse tooling that assumes strict primary-key/foreign-key joins (see [bridge table tooling workarounds](bridge-table-tooling-workarounds.md)), but it offers more flexibility and simpler reporting than flattening as the number of simultaneous values grows.

If the groups themselves are meaningful, named business entities in their own right (e.g. a standing "Eastern Special Project Team" with its own descriptive attributes and natural key), model the group as its own dimension table instead, with its members captured as a multivalued attribute of *that* dimension — the ordinary bridge-table pattern described above, rather than a bridge sitting directly between the fact table and a member dimension.

## Positional design vs. bridge table

Two design choices exist for a multivalued dimension attribute (e.g. a business customer that legitimately operates in more than one industry):

- **Positional design (flattening)**: spread the values into a fixed number of named columns (e.g., `industry_1`, `industry_2`, `industry_3` instead of one multivalued industry attribute). This is the simplest option, but only holds up when three conditions are all true: a bounded, fairly small number of values is acceptable to the business; each repeating column corresponds to a clearly identifiable role (so `home_phone`/`office_phone`/`mobile_phone` works, but `industry_1`/`industry_2`/`industry_3` does not, since there's no natural ordering); and no fact-table query will ever need to filter or group by a value that could appear interchangeably in any of the columns — multi-condition filtering across every repeating column, and grouping results by whichever column happens to hold a match, gets unmanageable fast. Works well up to roughly 100 columns for the pure column-count concern; low-cardinality columns benefit from bitmapped indexes, and columnar databases handle wide sparse positional schemas comparatively well.
- **Bridge table**: rows exist only when needed, scaling gracefully to open-ended attribute sets, but requires SQL complex enough that it must be hidden from direct business-user view, and may exceed what some BI tools can generate natively.

Beyond roughly 100 columns — especially for frequently-added, open-ended attribute sets like name-value pairs, where the value can be numeric, textual, a file pointer, a URL, or even a recursive reference to further name-value data — a bridge table is the appropriate design; [outrigger dimension](outrigger-dimension.md)s and [mini-dimension](slowly-changing-dimension-type-4.md)s don't scale gracefully for very large, expanding indicator sets.

## Time-varying bridge tables

A multivalued bridge table may itself need to be based on a [slowly changing dimension type 2](slowly-changing-dimension-type-2.md) — for example, a many-to-many bridge between bank accounts and customers, where both underlying dimensions are type 2. To prevent incorrect linkages across time, the bridge table must include effective and expiration date-time stamps of its own, and the requesting application must constrain to a specific moment in time to get a consistent snapshot — the same discipline required of [ragged hierarchy bridge table](ragged-hierarchy-bridge-table.md)s under time-varying hierarchy changes. This applies to a bridge sitting between the fact table and a dimension (as above); time-stamping the bridge rows themselves generally only makes sense for that case.

When the bridge instead sits between a *dimension* row and an outrigger holding its multivalued attribute (e.g. customer → industry-group bridge → industry outrigger), a change in *which* values are grouped together is best treated as a change to the dimension itself, not to the bridge: the group a dimension row points to is itself one of that row's characteristics, so a type 1 response simply repoints the dimension row's group key to a different (possibly pre-existing) group, while a type 2 response issues a new dimension row referencing a new group, leaving the old dimension row's group — and every fact already tied to it — untouched. A time stamp belongs on the *dimension* row to capture the effective period of a particular grouping in this case; adding time stamps to the bridge rows themselves adds no extra information and forces a separate group per distinct combination of values. Separately, a type 2 change to the outrigger itself (e.g. an industry gets renamed or split) ripples further: every dimension row referencing the old outrigger value needs its own type 2 change and a new bridge group for the new combination, or facts already recorded lose their correct historical association.

## Folding a small outrigger into the bridge

When there are only one or two multivalued attributes involved, the separate outrigger table can be eliminated by storing its columns directly on the bridge (group) table itself, instead of joining out to a distinct outrigger. This reduces the table and join count, at the cost of redundant storage of the attribute values across bridge rows — accepted as ordinary in dimensional design — and requires care to keep the repeated values (e.g. an industry name) consistent and indexed wherever they recur.

## Adding a mini-dimension inside a bridge table

A bridge table built on dimensions tracked with [slowly changing dimension type 2](slowly-changing-dimension-type-2.md) can itself explode in size over time, the same way a [self-referencing outrigger](outrigger-dimension.md) does — every type 2 change on either side of the bridged relationship can force new bridge rows. If one of the bridged dimensions is a large, rapidly changing "monster dimension" (fast-moving demographic or status attributes, for example), the standard [type 4 mini-dimension](slowly-changing-dimension-type-4.md) fix still applies, but the mini-dimension's foreign key must be added *inside the bridge table itself* rather than directly on the fact table, since that dimension is only reachable through the bridge in the first place. The bridge table's key becomes the combination of both bridged entity keys plus the mini-dimension key, linking each pairing to the attribute snapshot in effect at that point — change tracking pressure on the bridge is then bounded by how often the fact table itself is loaded (e.g., only at month-end for a monthly [periodic snapshot fact table](periodic-snapshot-fact-table.md)), rather than by every incremental attribute change.

## Caution: scope discipline

Keep a bridge table's dimension scoped to values genuinely relevant to the relationship it represents — don't let it become "a dumping ground for every employee or citizen or salesperson or human being the organization interacts with," a risk called out specifically for multi-contact bridge tables.

A [ragged hierarchy bridge table](ragged-hierarchy-bridge-table.md) is a specialized application of the same underlying bridge table pattern, applied to parent-child paths in a tree rather than to an unordered group of simultaneous values.
