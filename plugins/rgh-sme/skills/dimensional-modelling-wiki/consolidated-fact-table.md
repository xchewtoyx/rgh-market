A consolidated fact table combines facts from multiple [business process](business-process.md)es at the same [grain](grain.md) into one physical table — for example, sales actuals consolidated with sales forecasts. This simplifies actual-vs-forecast style analysis compared to [drilling across](drilling-across.md) separate fact tables at query time, at the cost of extra ETL burden to bring the source processes into alignment during load. It is one instance of a [derived schema](derived-schema.md) — a table built by restructuring already-loaded dimensional data rather than sourced fresh from operational systems — also called a **merged** or **drill-across fact table**; the three names are interchangeable.

Consider a consolidated fact table for cross-process metrics that are frequently analyzed together; it eases the BI-layer analytic burden by moving the integration work into ETL, done once, rather than requiring every query to drill across. Building it does not remove the need for explicit business rules about differing cardinality between the source processes — for example, whether a consolidated solicitations-and-responses table should include every solicitation and every response, or only matched pairs where a response actually followed a solicitation — the same cardinality mismatch that makes a direct [fact-to-fact join](drilling-across.md) unsafe still has to be resolved somewhere, just once in ETL instead of on every query.

## Grain and dimensionality must match

Every source fact table folded into a consolidated fact table must be aggregated to the same [grain](grain.md) and dimensionality as the others — since the source processes rarely share a natural common grain on their own, building the consolidated table forces eliminating or aggregating dimensions down to their least common denominator, while the original, more granular data is retained separately in its own atomic-grain fact tables rather than discarded. Two related risks follow from this: designing solely around the consolidated grain and then failing to meet a requirement that needs finer drill-down than the consolidated table can offer, or worse, force-fitting differently-grained source data into the consolidated table using artificial facts or dimensions to paper over the mismatch. Both should be avoided — a consolidated fact table is a supplement to the atomic-grain fact tables for one specific, frequently-recurring cross-process question, not a replacement for them.

A consolidated table can also acquire spurious rows from the reduced grain: if one source process has activity for a dimension combination that another doesn't (a March sales goal for a territory with no actual March orders, say), the combined row still gets built with the missing side's facts at zero — a report against the consolidated table alone would show a spurious zero-order row for that territory, while a territory with orders but no goal wouldn't appear at all. This is the same zero-row artifact that comes from ever recording two different processes' activity in one fact table, and it's a further reason to keep querying the single-process star directly whenever the question doesn't actually need the cross-process comparison.

## Build it last, from already-loaded atomic stars — not first, from source

Stakeholder pressure often pushes toward building a highly summarized consolidated table (a "360° customer view," a profitability mart combining revenue with every cost element) directly from operational sources, as a fast route to an executive KPI dashboard. This is close to the last thing that should actually be built first: beyond the ETL risk of integrating several operational sources at once with no incremental delivery along the way, the lack of underlying atomic-grain detail undermines the dashboard's own credibility the moment a user tries to drill down and explain one of its numbers and can't. Build a consolidated fact table as a genuinely [derived](derived-schema.md) table instead — sourced from already-loaded, already-[conformed](conformed-dimensions.md) atomic-grain fact tables for each contributing process, once those exist — rather than as the first thing built from raw sources. This mirrors the same atomic-grain-first discipline that applies to [grain](grain.md) declaration generally: a summary can always be derived from atomic detail on demand, but atomic detail can never be reconstructed after the fact from a summary that was built without it.

## Dimensions present in only one source

A dimension that exists in only one of the source fact tables (a plan-version dimension on a goals star with no counterpart on the actuals star, for instance) needs an explicit decision during design, not an implicit one during ETL. Omitting it from the consolidated table is simplest, but silently limits the table to whichever single value ETL selected (e.g., only the most recent plan version) with no way to compare versions later. Including it instead lets the consolidated table track every value of that dimension, at the cost of repeating the other source's facts once per value during ETL — which in turn means every query against the consolidated table must constrain that dimension to a single value, or the repeated facts get double- or triple-counted. Whichever choice is made, document it and, where possible, enforce the required constraint through a pre-constrained view or a BI tool prompt rather than relying on every report author to remember it.
