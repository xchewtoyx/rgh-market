Unlike a database index, an [aggregate fact table](aggregate-fact-table.md) doesn't achieve invisibility for free — it needs both queries rewritten to use it and ongoing maintenance to stay in sync with the base star, and nothing forces either automatically. Tooling that handles the first half is an **aggregate navigator**: it intercepts a query written against the base star and transparently redirects it to the smallest aggregate that can still answer it (identifying candidates from stored aggregate/grain metadata, and picking among them by comparing fact-table row counts), returning results as if the base star had been queried directly. This can live in the reporting tool, in the DBMS itself (often called query rewrite), or in an intermediary — and it's what makes it possible to add or remove an aggregate later without revisiting every report that might benefit from it, provided the rewriting genuinely happens at query execution time rather than being baked into a report at design or compile time. A navigator that operates at true runtime can also unlock further capabilities: taking a specific aggregate offline for rebuild while queries transparently fall back to slower alternatives, or redirecting a query to a different physical database, vendor, or even an [olap-cube](olap-cube.md) instead of a relational aggregate.

Without a navigator, choosing which of several available aggregates (or the base star) best answers a given query — the one with the fewest fact-table rows among those still holding the needed dimensionality — falls to whoever writes the query. This is manageable for an experienced developer working from schema and size documentation, but is described as "bewildering" for less experienced or ad hoc users, especially once a report's dimensions change mid-analysis and invalidate whichever star was originally chosen. The two manual mitigations both trade something away: restrict aggregate access to trained developers so end users never face the choice (but then get no aggregate benefit at all), or expose aggregates to trained developers only (but every report then becomes hard-coded to a specific aggregate, needing rework whenever a better-fit aggregate is added or an existing one is retired).

Separate from navigation, an aggregate need not match a query's exact grain to help it — as long as it holds the dimensionality a query needs (or finer), the DBMS can further summarize the aggregate's own rows at query time and still capture most of the precomputation benefit. Because no single aggregate can serve every query, multiple aggregates typically pre-summarize the same base star across different dimension combinations rather than as successive levels of one summarization chain, maximizing how many queries benefit. Some queries can never be served by any aggregate at all — anything that needs access to genuinely granular detail (filtering order lines by an individual line's dollar value, say) must still hit the base star, though having aggregates in place for other queries still indirectly helps by freeing up shared system resources.
