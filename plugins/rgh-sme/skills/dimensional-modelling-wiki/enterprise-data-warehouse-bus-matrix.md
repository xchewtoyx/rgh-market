The bus matrix (also called the conformance or event matrix) documents and communicates the [enterprise data warehouse bus architecture](enterprise-data-warehouse-bus-architecture.md). Rows are [business process](business-process.md)es (never organizational departments); columns are common, [conformed dimensions](conformed-dimensions.md) across the enterprise — it's useful to draft a core-dimension list before filling in the matrix. Cells are shaded or marked to show which dimensions apply to which process. Typical matrices are "surprisingly square," roughly 25–50 rows by a comparable number of columns.

A plain table diagram naming which stars share which dimensions (rather than a matrix) becomes unreadable once column-level detail and a realistic number of dimensions and fact tables are added, and it can't represent non-identical (rollup) conformance relationships — this is why the matrix, not a diagram, is the standard planning tool. Base dimensions and their [shrunken dimension](shrunken-dimension.md) rollups are grouped or shaded together under one column heading (e.g. day/month/quarter grouped under "day"; salesrep/territory/region grouped under "salesrep"), and [degenerate dimension](degenerate-dimension.md)s used for drill-across (e.g. an `order_line` control number shared across fact tables) belong on the matrix too, alongside true dimension tables. The matrix need not list every dimension in the warehouse — only those linking processes together; dimensions localized to a single fact table can be omitted. Large implementations often pair one high-level enterprise matrix with additional, more detailed per-subject-area matrices.

Within a grouped rollup column, mark a process row under every rollup level its own dimension can validly reach, not just its most granular one — a fact table built at full salesrep detail should be checked under "salesrep," but also under the coarser "territory" and "region" columns it rolls up to. This turns the matrix into a direct lookup for valid [drilling across](drilling-across.md) pairings: any column with a shared checkmark between two process rows identifies a level both can be compared at (a fact table with only territory-level detail sharing a checkmark under "region" with a full-detail salesrep fact table, for instance), without requiring a reader to separately reason about which rollups are implied.

A **detailed implementation bus matrix** expands each process row further into specific fact tables or OLAP cubes, at which level precise [grain](grain.md) statements and fact lists can be documented.

## Uses

The matrix serves architecture planning, database design, data governance coordination, project estimating, and organizational communication simultaneously. Because dimensions are envisioned across processes (owned by data governance, built by the DW/BI team) rather than designed in isolation for one process, they supply the integration glue that enables [drilling across](drilling-across.md). Multiple teams can build matrix rows independently and asynchronously with confidence the results will fit together. A row's dimensionality gives project managers a rough sense of implementation effort (fewer dimensions, especially ones already built, usually means less work). The matrix also identifies which business experts should serve as data governance leaders for each conformed dimension.

A companion **opportunity/stakeholder matrix** keeps the process rows but replaces dimension columns with business functions (e.g., marketing, sales, finance); shaded cells show which functions are interested in which process, identifying who to invite to collaborative design sessions once a row becomes a project.

## Common mistakes

- **Rows**: avoid departmental or overly encompassing rows (a row should not mirror an org chart) and avoid report-centric, too-narrow rows — a row is a business process, not a laundry list of requested reports; a single process supports many analyses.
- **Columns**: avoid overly generalized columns that conflate unrelated entities with near-zero overlap (e.g., a generic "person" column merging employees, suppliers, and customer contacts, or a generic "location" merging facilities, employee addresses, and customer sites). Avoid a separate column per hierarchy level — columns should represent the most granular dimension, with any higher rollup grain noted textually within the cell rather than modeled as its own column (see [shrunken dimension](shrunken-dimension.md)). Treating every dimension attribute as its own column defeats the purpose of the matrix.

## The data warehouse matrix: tracking actual conformance, not planned conformance

The bus matrix is a **planning** tool reflecting what stakeholders want conformed; a companion **data warehouse matrix** is a **management** tool reflecting what has actually been built — copy the bus matrix's rows and columns over to the real, physical fact and dimension tables, and add technical columns such as data sources, fact table type, primary time-dimension granularity, and volumetrics. The two documents are expected to drift apart over time (a sprint compromise ships a dimension that isn't fully conformed yet, or an inherited legacy star never went through conformance at all) — that drift is exactly the information the data warehouse matrix exists to surface.

Where conformance has failed or been postponed, record it with **dimension version numbers**: keep one column per intended conformed dimension, but number each distinct non-conformed version actually in use against it, reserving the highest number for the most current or most authoritative version — a product dimension with three incompatible versions across manufacturing, sales, and customer support, for instance, is really three numbered versions under one intended column, not a single conformed dimension yet. After each delivery cycle, feed conformance failures discovered this way back into the planning-side bus matrix, so the next round of stakeholder modeling can prioritize refactoring older, non-conformed stars against the newer conformed version.

## Building the matrix collaboratively, event by event

The matrix can be built incrementally in the same modelstorming sessions that discover [business process](business-process.md)es, rather than assembled afterward from finished designs. As each event is added as a new row, mark its columns two ways rather than with a single checkmark: a plain tick means the event merely *references* that dimension, while a distinguishing mark (e.g. `*`) means the event can *create new values* for it — asking "can this event create new values for this dimension?" separately from "does this event use this dimension?" surfaces which process actually owns a dimension's data, useful later when deciding which system should be the [system-of-record](agile-data-profiling.md) for it.

As each new event is discovered ("what happens next?", or simply pointing at the last-added row and asking "who does what?" again), check any of its apparently-new dimensions for **synonymy** against dimensions already on the matrix, grouped by W-type, before adding a new column — a "warehouse worker" surfacing alongside an existing "salesperson" column, both being *who* details, prompts asking whether the two are really the same type of thing (both employees), which is exactly how a [role-playing dimension](role-playing-dimension.md) gets discovered: renaming SALESPERSON to a conformed EMPLOYEE dimension while the event's own column keeps its role-specific label. Discovering this kind of reuse opportunity is far cheaper at matrix-design time than after a star schema has shipped, which is itself an argument for modeling several related events early rather than one at a time in isolation.

### Finding missing events and marking exceptional ones

Once several events are placed on the matrix, resume asking "who does what?" without worrying about strict chronological order — missing events are easier to spot as *gaps* once the events stakeholders freely offered are already laid out next to each other, by asking directly: "does anything happen between X and Y?" An optional or exceptional event (one that applies to only a small fraction of instances of the events around it — a return following a shipment, say) is documented by **bracketing its name**, a visual cue that it might warrant separate handling (its own smaller-volume process) rather than folding into a mandatory milestone sequence. Events that resist being placed in a strict sequence — simultaneous, looping, or mutually exclusive with a neighbor — don't need to be forced into a false order; place them next to each other in whatever relative position stakeholders agree on. Documenting the first and last event of a process is worth prioritizing specifically, since together they represent the process's cause and effect, origin and outcome, and are the minimum needed for any process-performance measurement spanning the whole thing.

### Process sequences surface through shared why/how

Asking *why* an event happens, immediately followed by *how* you'd know it happened, often reveals that one event's *how* detail (its [degenerate dimension](degenerate-dimension.md) — an order ID, say) is effectively the *next* event's *why* detail: a warehouse worker ships a product "because a customer ordered" it, evidenced by the shipment record carrying the same order ID. A [degenerate dimension](degenerate-dimension.md) shared this way across two or more events on the matrix — ticked (referenced) on the later events but starred (created) only on the first — is a strong, checkable signal that the events form a **process sequence**: candidate milestones of a single evolving event, worth modeling together later as an [accumulating snapshot fact table](accumulating-snapshot-fact-table.md). Confirm the sequence is genuine by probing edge cases with stakeholders (samples or replacements shipped without a prior order, say) — if these are out of scope, or are handled as "pseudo" orders that still generate the same kind of ID, the sequence still holds.

### Rating dimensions and events for scope

Once several events are on the matrix, stakeholders can rate each one's business importance to help decide what to model in detail next and prioritize for the next release; higher-importance dimensions generally rate above the highest-importance event that uses them, since a fact table can't be built before its dimensions are. This rating exercise is a project-prioritization technique, not a modeling one, and belongs to sprint/backlog planning rather than the schema design itself.

## Retrofitting existing models

Isolated dimensional models built without a conformance framework deliver irreconcilable views and entrench incomparable reports — "worse than simply a lost opportunity," since they become legacy blockers to a coherent environment. If an existing model's design is otherwise sound, its dimension can sometimes be remapped to a standardized, conformed version via a cross-reference map, with the fact table reprocessed to swap keys (differing attributes still force BI application rework). More often, stovepipe models have deeper design errors — wrong grain, missing dimensionality — such that retrofitting costs more than rebuilding from scratch.
