Financial services and similar businesses offer disparate product lines that are still all instances of one broader concept — a bank's checking accounts, mortgages, and business loans are all "accounts," but each has largely incompatible facts and attributes. A single consolidated [fact-table](fact-table.md) with the union of every possible fact and attribute across all product types fails, because hundreds of incompatible facts and attributes end up mostly null on any given row. Beyond the sheer column-count problem, a single blended table is also semantically risky: nothing stops a query from combining a fact meaningful to one subtype with a dimension attribute meaningful only to another (a subscription's cover-price fact joined against a book-specific author attribute, say), producing a report that runs without error but means nothing. A single unified table is still the right choice when subtype variation is modest — the supertype/subtype split below is worth its extra complexity specifically when variation is extreme or this incompatible-combination risk is real.

The solution is a supertype/subtype design (also called core and custom fact tables): a **supertype** fact table holding the intersection of facts common to every product type, paired with a supertype [dimension-table](dimension-table.md) of common attributes, plus separate **subtype** fact and dimension tables per product type holding whatever is specific to that type. [Generic multipurpose attributes](generic-multipurpose-attributes.md) address the same heterogeneous-attribute problem from a different angle, trading query accessibility for open-ended storage flexibility, and can be combined with this pattern rather than used in its place. Common cross-product-type analysis uses the supertype tables; type-specific analysis drills into the relevant subtype tables. This pattern is needed specifically "when a business has heterogeneous products that have naturally different facts and descriptors, but a single customer base that demands an integrated view" — cramming every product type's special attributes into one shared dimension instead produces a table riddled with data holes, mostly null on any given row, the same failure mode a single blended fact table would have.

## Duplicating supertype content into each subtype schema

Each subtype schema duplicates the supertype facts and attributes alongside its own type-specific ones, so a user analyzing one line of business never needs to join across the supertype and subtype schemas to see the complete picture for that line — an analysis either goes through the single supertype fact/dimension pair for a cross-product view, or through exactly one subtype schema for a deep, single-product-type view. Combining data from two different subtype schemas in one query generally doesn't make sense, since by definition their facts and attributes are disjoint (or nearly so) between lines of business; this disjointness makes the subtype tables a clean **partitioning** of the full account/product population, with no overlap between subtype schemas. If the lines of business are physically separated across different locations, the subtype tables likely won't reside alongside the supertype tables at all — in that case the supertype table's content is simply duplicated, once, into each of the subtype tables that need it.

## Shared surrogate keys

A subtype dimension is a row-subset [shrunken dimension](shrunken-dimension.md) with extra columns layered on top: it holds only the rows belonging to that one product type, like an ordinary shrunken dimension, but unlike one it also carries additional attributes specific to that type rather than being a strict subset of the supertype dimension's columns. Critically, each subtype dimension row uses the **same surrogate key** as its corresponding row in the supertype dimension — a specific product's key is identical whether looked up through the supertype product dimension or through the one subtype product dimension it belongs to. This lets ETL and any cross-referencing logic treat the supertype key as the single source of truth for identity, with subtype tables simply exposing more detail about a subset of those same keys.

## The implicit-filter trap when a subtype fact table is skipped

Even when every product type shares the same facts (so a per-type *fact* table seems unnecessary, only per-type dimension tables), still build the subtype fact table — or a view standing in for one. Joining a shared fact table to a subtype dimension table implicitly restricts the query to that subtype (joining to `subscription_product` silently adds the equivalent of "where product type = subscription," with no explicit filter clause needed) — which works fine until the query is later refined, for example by removing a grouping attribute that happened to be the only reason the subtype dimension was in the join at all. Removing that attribute can silently remove the implicit type filter along with it, and a total like `order_dollars` jumps because the query now spans every product type instead of just the one intended, with nothing about the query's own SQL flagging the change. Building the subtype-scoped fact table (or view) explicitly, and joining to *that* instead of relying on an incidental dimension join to carry the filtering, keeps the query's scope tied to which fact table it reads from rather than to which attributes happen to still be present in the `SELECT` or `GROUP BY`.

## Terminology: swappable dimensions

The subtype dimensions in this pattern are also called **swappable dimensions**: because every subtype shares the supertype's surrogate key, a query or BI semantic layer can substitute one subtype dimension for another (or for the supertype) without changing anything else about the query. This is exploited for both usability and performance — a business unit whose users only ever care about one product type can rename that subtype table to the generic "customer" or "product" name via a database synonym or view, so their default queries see only their relevant rows and columns without an explicit `WHERE` clause, and gain a performance benefit if that subtype is a small fraction of the full population. A **hot swappable dimension** goes a step further, structuring several swappable options with identical column names so that swapping between them requires no query rewriting at all — see [hot swappable dimension](hot-swappable-dimension.md) for that variant's other uses (row-level security, sample study groups, national-language translation).

## Spotting the need for this pattern during attribute discovery

Before any physical split is decided, mutually exclusive groups of attributes discovered while documenting a single dimension are the earliest signal that it is heterogeneous and may need this pattern. If members can only ever have values for one of two (or more) attribute groups — never both — the dimension likely mixes distinct member types (a CUSTOMER dimension mixing consumers, described by date-of-birth and gender, with businesses, described by SIC code and employee count). Each such group needs a **defining characteristic**: one or more attributes whose own value determines which group applies to a given member (e.g., CUSTOMER TYPE). A good defining characteristic is low-cardinality and mandatory, and typically becomes an important dimension hierarchy level; an optional or high-cardinality defining characteristic, or a dimension awash in exclusive attribute groups, is itself a warning sign of a struggling "one size fits all" generic dimension design. Exclusive groups can nest (a business-only "for profit / non-profit" split sitting inside the wider business-vs-consumer split). Recognizing this pattern early, during discovery, is what motivates evaluating the supertype/subtype split (or [generic multipurpose attributes](generic-multipurpose-attributes.md)) described below, rather than continuing to bolt every group's attributes onto one increasingly sparse dimension table.

## Sub-case: heterogeneous attributes but common facts

Some business processes capture metrics that don't vary by product type at all (a bank's new-account solicitation event, for example) — a single supertype fact table is then sufficient on the fact side, with no subtype fact tables needed. The product or account attribute heterogeneity can still be rich enough to warrant the full portfolio of subtype **dimension** tables even without matching subtype fact tables: the supertype dimension serves cross-product analysis, and a subtype dimension is used whenever a query needs that one type's specific attributes, joined back to the same shared supertype fact table via the shared surrogate key.
