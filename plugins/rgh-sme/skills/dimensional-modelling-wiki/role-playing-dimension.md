A role-playing dimension is a single physical [dimension-table](dimension-table.md) referenced multiple times by the same [fact-table](fact-table.md), where each reference plays a logically distinct role. The most common example is a [date dimension](date-dimension.md) referenced several times on one fact row — order date, ship date, delivery date — each a separate foreign key pointing at the same underlying table.

Each foreign key must be exposed through a separate view of the dimension with uniquely relabeled attribute column names (a "role"), so that the different references stay independent and unambiguous in reports and SQL — a query joining on ship date must not accidentally pick up column names that collide with the order date role. [Accumulating snapshot fact table](accumulating-snapshot-fact-table.md)s, which carry a date foreign key for every pipeline milestone, are built almost entirely out of role-playing date dimensions. A supplemental date dimension attached to another dimension table as an [outrigger dimension](outrigger-dimension.md) (e.g., a store's "first open date") is another common application of the same role-playing pattern, with columns distinctly relabeled to avoid confusion with the primary date dimension joined to the fact table.

To capture both universal standard time and local time in a multi-time-zone application, place dual foreign keys in the fact table joining to two role-playing [date dimension](date-dimension.md) (and potentially time-of-day dimension) references — one for standard time, one for local time — rather than trying to encode the offset as a plain attribute.

## Embedded who: a dimension referencing another dimension directly

A dimension can also carry a relationship to another "who" entirely on itself rather than through the fact table — a customer dimension's account manager (an employee) or parent company (another customer), for instance. Modeled naively as a [type 2](slowly-changing-dimension-type-2.md) foreign key sitting directly on the primary dimension, this turns the primary dimension into a rapidly-changing dimension by proxy: every time the referenced entity's own assignment changes, the primary dimension needs a new row too. The usual fix combines two techniques already covered elsewhere: keep the relationship as a [type 1](slowly-changing-dimension-type-1.md) (current-value) foreign key directly on the primary dimension for simple "current" reporting and ETL lookups, and separately expose the full history of the relationship at fact time through either a shortcut join or an [outrigger dimension](outrigger-dimension.md) view of the referenced dimension, playing a role such as "current account manager." When the referenced dimension is the *same* dimension referencing itself (a parent company that is itself a customer), the relationship becomes a recursive foreign key and the modeling problem shifts to representing a [ragged (variable depth) hierarchy](ragged-hierarchy.md) rather than a role-playing one.

Avoid the temptation to build a single combined date dimension keyed by the combination of roles (e.g. one row per order-date/requested-ship-date pair) instead of separate role-playing views — it balloons what would otherwise be a roughly 365-row-per-year table into the cross product of the roles, and the result no longer [conforms](conformed-dimensions.md) to the daily, weekly, or monthly date dimensions used elsewhere.

On the [enterprise data warehouse bus matrix](enterprise-data-warehouse-bus-matrix.md), document role playing either by listing the multiple roles within a single dimension-column cell (the most common technique, also used for [shrunken dimension](shrunken-dimension.md)s), or, when the same small set of roles recurs across many processes, via subcolumns within one conformed dimension column. Role-playing reuses one physical dimension across several roles of the *same* kind of thing; contrast this with the riskier [abstract generic dimension](abstract-generic-dimension.md) generalization, which merges genuinely dissimilar entity types into one dimension and is justified only in narrow cases.

## Exception: combining two roles into one dimension

Roles of the same dimension should normally stay logically separate — exposed as distinct views over one physical table — rather than merged. The narrow exception is when the roles are small in volume and tightly correlated, and an attribute genuinely depends on the *combination* of both roles for its meaning. For example, analyzing both the booking class a passenger purchased and the class they actually flew, plus an upgrade/downgrade indicator, could use two role-playing class-of-service dimensions (4 rows each) plus a separate 3-value indicator dimension — but because class of service has only a handful of values, combining purchased-class, flown-class, and the derived class-change indicator into a single dimension (a Cartesian product of a few dozen rows) is simpler to query and lets the indicator's meaning live directly alongside the two roles it describes, without extra join or application-side logic to derive it. This combined dimension is itself a form of [junk dimension](junk-dimension.md), built from correlated, low-cardinality attributes. Other fact tables that don't need this combined context keep referencing the plain, uncombined conformed dimension.

This same small-and-correlated test governs whether two role-playing instances of a *large*-volume dimension (e.g., origin and destination airports) are worth combining: with only a handful of values, combining is cheap and adds convenience; with a large or open-ended value space, the combined table's row count and attribute duplication (a couple dozen attributes apiece, doubled) usually make keeping the roles as separate dimensions the more practical choice, even though the relationship between them is technically many-to-many. In that large-volume case, a [bridge table](bridge-table.md) is not needed either — the many-to-many relationship between the two roles can be represented directly within the fact table's own multiple foreign keys (one per role), without introducing a separate multivalued-dimension structure, whenever each fact row genuinely has exactly one value for each role.
