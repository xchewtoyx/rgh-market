An outrigger dimension is a [dimension-table](dimension-table.md) referenced from within another, primary dimension table — for example, a bank account dimension carrying a foreign key to a separate "date account opened" dimension, rather than storing that date's calendar attributes as plain flattened columns. It is a permitted, limited form of [snowflaking](snowflake-schema.md), justified specifically when the business needs to filter or group the secondary attribute by non-standard calendar attributes (fiscal period, business-day indicator, holiday period) that only a real dimension table can supply — otherwise a plain date-type column is sufficient. Outrigger dates must stay within the range of the standard [date dimension](date-dimension.md).

Outriggers are permissible but should be the exception rather than the rule: a dimensional model "should not be littered with outriggers." Downsides are the same as snowflaking generally — more joins hurting performance, and reduced legibility and browsing ability for users.

Beyond the non-standard-calendar-attribute case, an outrigger is also justified for a sizable block of attributes that is genuinely at a coarser, materially different grain than the primary dimension and identical across many of its rows — for example, on the order of 150 external demographic or socioeconomic attributes tied to a customer's county of residence, identical for every customer in that county. The justification there is threefold: the data sits at a different analytic grain than the primary dimension, it is loaded on its own separate schedule, and folding it directly into the primary dimension would waste significant space across a very large dimension by repeating the same values on every matching row. A view declaration can present the outrigger joined back to its parent, hiding the extra join from query tools or users that expect a strict star schema.

## Explosion risk and demoting to the fact table

A foreign key from a base dimension to an outrigger can cause explosive growth of the base dimension, because a [slowly changing dimension type 2](slowly-changing-dimension-type-2.md) change in the outrigger forces corresponding type 2 processing in every base dimension row that references it. This growth can be avoided by demoting the correlation — placing the outrigger's foreign key directly on the [fact-table](fact-table.md) instead of on the base dimension — at the cost that the correlation is now only discoverable by traversing the fact table. This is acceptable, and often preferable, for a [periodic snapshot fact table](periodic-snapshot-fact-table.md), where every dimension key is guaranteed present each period anyway.

The worst case of this explosion is a **self-referencing outrigger**, such as an employee dimension's "manager" attribute pointing at another row of the same employee dimension. If the manager key is tracked as type 2, then a type 2 change anywhere in the manager's own profile (even something as unrelated as a home-address update) forces a new dimension row not just for the manager but for every subordinate whose manager key points at them — and if that manager is senior enough (e.g., the CEO), a single unrelated profile edit can cascade a new row for every employee in the organization. If the business doesn't actually want manager profile changes tracked through this cascade, the fix is to make the manager reference a [type 1](slowly-changing-dimension-type-1.md) attribute pointing at the manager's **durable key** (joined to a role-playing view of the dimension limited to each manager's current row) instead of their type 2 surrogate key — this always shows the *current* manager and sacrifices manager-change history on that attribute, but stops the cascade entirely.
