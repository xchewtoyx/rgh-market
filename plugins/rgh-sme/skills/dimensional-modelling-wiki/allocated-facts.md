Operational transaction systems often have a header row tied to multiple line rows — an order header with several order lines, an invoice header with several invoice lines. In a **header/line (parent/child) fact table** design, all header-level dimension foreign keys and [degenerate dimension](degenerate-dimension.md)s should be included directly on the line-level fact table, so the line-grain table stands alone as the primary analytic table.

Header/line data commonly includes facts captured only at the coarser header grain — a header-level freight charge, for instance — that don't naturally belong to any one line. The recommended technique is to **allocate** header facts down to line grain using business-provided rules (e.g., proportional to line value or weight), so the allocated fact can then be sliced and rolled up by every dimension attached to the line-level [fact-table](fact-table.md). Allocation often avoids needing a separate header-level fact table at all, unless a header table offers a specific query performance advantage. Getting organizational agreement on the allocation rule itself is often political (e.g., finance wants freight allocated by extended gross amount while logistics wants it allocated by product weight) and is best owned by the business function that owns the metric, such as finance, rather than by the DW/BI team — so the modeling project isn't delayed by the negotiation. If no single scheme can be agreed, the fallback is exposing multiple, uniquely labeled allocated versions of the same metric on every line rather than picking one; a single standard allocation is still preferable when it's achievable.

Two alternative techniques for handling an unallocated header fact are discouraged: repeating the unallocated header amount on every line (risks overstating the total when the lines are summed) and storing it only on the first or last line (avoids overcounting but silently disappears from any query that filters on a product attribute and happens to exclude that line). A related trick — flagging a row as carrying the header fact via a special dimension key such as a reserved product code — is also discouraged, since it adds a "decoder ring" layer of complexity that dimensional models should avoid.

## Two header/line anti-patterns to avoid

Two mistakes are common because they both still "accurately represent the data relationships," so they don't obviously stand out as wrong, and both feel natural to modelers or ETL staff coming from a transaction-processing background:

- **Treating the transaction header as a dimension.** Replicating the operational order header as a dimension keyed by, say, order number, while leaving the line-item fact table with little dimensionality of its own. This fails because the header dimension ends up far too large relative to the fact table (e.g., 5 lines per order makes the "dimension" 20% as large as the fact table, when dimensions should be orders of magnitude smaller than facts), it doesn't grow at the same rate as the fact table, and any analysis of order-level characteristics (customer, rep, deal) requires traversing this oversized dimension.
- **Not inheriting header dimensionality into the line facts.** Making the order header its own fact table with its own surrounding dimensions, while the line-item fact table joins to it via order number instead of carrying the header's dimensions directly. This fails because slicing line facts by any header attribute now requires joining a large header fact table to an even larger line fact table, instead of a simple direct join from the line fact table to its own dimensions.

The fix in both cases is the header/line pattern described above: push every header-level dimension foreign key and degenerate dimension down onto the line-grain fact table directly, so it stands alone as the primary analytic table.

## Profit and loss fact tables using allocations

Fact tables that expose the full profit equation (revenue − costs = profit) at the [grain](grain.md) of the atomic revenue transaction, with many separate cost components, are among the most powerful DW/BI deliverables — they enable customer, product, promotion, and channel profitability rollups. They are difficult to build because every cost component must be allocated from its own source down to the fact table's grain; this allocation is often a major, politically charged ETL subsystem that requires high-level executive support, which is why profitability fact tables are typically not tackled in early implementation phases of a project.

A P&L fact table's line items are typically arranged top-to-bottom, from an undiscounted starting value down to what's left over after subtracting allowances, discounts, and every cost component — for example: extended gross amount, minus extended allowance and extended discount amounts (both allocated to the line if captured at header grain), giving an extended net amount; then further minus extended fixed and variable manufacturing cost, extended storage cost, and extended distribution cost, giving a final **contribution** amount. Every line item is an [additive fact](additive-fact.md) stated as an extended value (unit rate × quantity, not a bare unit rate) so the whole P&L can be correctly summed by any dimension and any rollup computed by summing the extended values first, never by averaging unit rates or already-computed ratios directly. The bottom line is usually called "contribution" rather than "profit," since it typically excludes general and administrative costs and other company-wide financial adjustments.

Even with activity-based costing or a robust ERP system, most source systems struggle to capture every cost component at true line-item grain, and each cost type may need its own extraction and transformation logic — ten cost facts can mean ten separate ETL pipelines to build and maintain. Assess source-system feasibility for each cost component in detail before committing to a granular P&L fact table, and be wary of the DW/BI team ending up responsible for driving organizational consensus on activity-based costing as a side effect of the project. Where time allows, it's often better to deliver revenue and each cost component as separate, simpler fact tables first, and tackle a fully consolidated P&L model — see [consolidated fact table](consolidated-fact-table.md) — only once those pieces are already sourced and working.
