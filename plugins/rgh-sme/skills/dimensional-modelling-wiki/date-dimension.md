The date dimension is attached to almost every [fact-table](fact-table.md), since nearly every business process captures a time series. Because calendar dates are fixed and predetermined, it can be built far in advance — 10-20 years of daily rows is only around 7,300 rows, a small table — and it is typically the first dimension in a database's partitioning scheme, so successive time-interval loads land on fresh disk territory.

Recommended columns include the day-of-week name, day number within the calendar month, month number within the year, long and abbreviated month labels, a year-month label for report headers, quarter number and year-quarter label, plus equivalent fiscal-period columns wherever the fiscal calendar differs from the standard calendar (see [multiple fiscal calendars](multiple-fiscal-calendars.md) for when more than one such calendar is in play). See [fixed-depth hierarchy](fixed-depth-hierarchy.md) for how multiple calendar hierarchies (e.g., day → month → year alongside day → fiscal period → year) coexist as parallel attribute sets on the same dimension row.

## Anti-pattern: fixed time series buckets instead of a date dimension

A legacy pattern carried over from operational systems repeats a whole set of metric columns once per period directly on one row — a "month 1," "month 2," ... "month 12" set of columns holding the same measures, instead of a proper date dimension with one fact row per period. This should be avoided: the hard-coded number of time slots is inflexible (running out of slots forces altering the table, or shifting every column's meaning down one slot, which breaks any query already written against the old column names); the date attributes themselves — calendar rollups, fiscal periods, holiday flags — become the responsibility of application code rather than a queryable date dimension; and the design is inefficient and null-heavy whenever a measurement isn't taken in every period. Recurring time buckets should instead become separate fact table rows, each referencing this dimension through an ordinary foreign key.

## Why an explicit dimension table, not a raw date column

Relying on native SQL date-type semantics on a fact table column to "avoid an expensive join" fails for three reasons: most relational optimizers already resolve dimensional joins efficiently, so there's no real cost to avoid; average business users don't know SQL date semantics; and SQL date functions don't support filtering by weekday/weekend, holidays, fiscal periods, or seasons — these are inherently non-standard calendar attributes with no general algorithmic definition (never compute Easter in SQL — look it up). Calendar logic belongs in a dimension table, not in application code.

## Textual attributes and current/relative flags

As with any [dimension-table](dimension-table.md), indicators like a holiday flag should be stored as meaningful text ("Holiday"/"Non-holiday") rather than a cryptic code, so attributes can be jointly constrained (e.g., comparing weekday holidays vs. weekend holidays) with self-explanatory results.

Most date attributes are immutable — June 1, 2013 always rolls up to June, Q2, 2013 — but some need daily updates as time passes: `IsCurrentDay`, `IsCurrentMonth`, `IsPrior60Days`, or custom corporate-calendar flags like `IsFiscalMonthEnd`. `IsCurrentDay` typically refers to the most recently loaded day (often "yesterday," since most warehouses load daily), not literally today. Lag-day columns (0 = today, -1 = yesterday, +1 = tomorrow) can be physically stored or computed at query time; similar structures can exist for month/quarter/year, though many BI tools already handle prior-period calculations, making these columns optional.

## Time-of-day

Date and time are usually kept separate to avoid row-count explosion: a 20-year date dimension is around 7,300 rows, but a one-row-per-minute grain balloons to 10M+ rows (1,440 minutes/day), and per-second grain would reach 31M+ rows/year. Since the date dimension is likely the most frequently constrained dimension in the schema, keeping it small matters. If users need to roll up or filter by day-part groupings (15-minute intervals, hours, shifts, lunch hour, prime time), model time-of-day as its own full dimension table instead — see [clock dimension](clock-dimension.md). If no such rollup or filter need exists, treat time-of-day as a simple date/time fact directly in the fact table instead — users are often more interested in time lags (transaction duration) than in discrete start/stop times, and lags are just differences between stored date/time stamps, which also allows computing gaps between transactions that span days, months, or years. When a fact table [role-plays](role-playing-dimension.md) both a date and a clock dimension for two related milestones (order date/time and delivery date/time, say), the elapsed duration between them is difficult to compute and aggregate through the dimensions themselves — store it directly as a fact instead.

## Primary key

The [surrogate key](surrogate-key.md) discussion covers why the date dimension is the sole exception to the rule against meaningful primary keys — it may use a `yyyymmdd`-formatted integer or a chronologically assigned sequential integer, primarily to support fact table partitioning, with a reserved key value for "date unknown at load time." Sequential, calendar-ordered date keys have a second benefit beyond partitioning: because they sort the same way the dates themselves do, they can be compared directly with `BETWEEN` in place of a full date/timestamp comparison, which matters for a [ragged hierarchy bridge table](ragged-hierarchy-bridge-table.md) or other effective-dated structure that needs to check a fact's date against a stored date range as cheaply as possible.

Two concrete key formats both satisfy this ordering property: an ISO `YYYYMMDD` integer (readable, and directly derivable from a source date without any surrogate-key lookup, which matters when many date-valued event details need converting per row) or an **epoch-offset** integer counted from a fixed origin date (smaller, contiguous values, which can suit some query optimizers better, at the cost of not being human-readable when setting up partition ranges). Either is a reasonable choice; whichever is picked, BI users and report authors should never be told the key format or encouraged to filter or decode it directly — the key exists for ETL and partitioning convenience only, and every BI-facing constraint should still go through the dimension's real descriptive attributes.

A companion set of **epoch counters** — a running day number, week number, or month number that increments once for every calendar day/week/month since the warehouse's earliest date, independent of calendar-year boundaries — makes "trailing N periods" filters (last 60 days, last 4 weeks) simple even when the window crosses a year boundary, without needing separate logic to handle the wraparound.

## Rollup (period) calendars

A [periodic snapshot fact table](periodic-snapshot-fact-table.md) or [aggregate fact table](aggregate-fact-table.md) built at week, month, or quarter grain should key against a matching rollup [shrunken dimension](shrunken-dimension.md) (a MONTH dimension, say) rather than joining to the day-grain date dimension directly through some day within the period (its last day, for instance). Joining to the day-grain table directly obscures the fact table's real granularity and invites a user to mistakenly group or filter monthly facts by a day-level attribute like day-of-week. A month rollup dimension is easy to build as a materialized view grouping the base date dimension by month; a convenient trick for keeping it usable by BI tools that expect a single unified date table is to give each month row the same key value as the date dimension's row for that month's last day (`MAX(date_key)` grouped by month) — a tool that can't work with two separate date-grain tables can then still join to the base date dimension directly and get correct-enough results, while a tool that supports the rollup dimension gets properly grain-explicit monthly attributes.

A related pattern where a business event is best understood relative to its own origin date rather than the standard calendar is an [offset calendar](offset-calendar.md).

## Actual versus scheduled dates: does a second date deserve its own dimension?

A process with both a scheduled and an actual timing for the same milestone (a scheduled versus actual arrival time, say) raises the question of whether the actual date should get its own role-playing date dimension foreign key alongside the scheduled one, for measuring on-time performance. The decision hinges on how much the actual date typically *diverges* from the scheduled one, not on whether the two are conceptually different: if actual timings rarely land on a different calendar date/period than scheduled — a flight running two minutes or even several hours late almost always still arrives the same day, or the very next one — then a separate ACTUAL DATE dimension adds an extra indexed foreign key that essentially never changes grouped-by-date answers, and can even distort them: a flight scheduled at 23:59 on March 31 but arriving two minutes late would report against a different fiscal quarter than the one it was scheduled for, purely from a marginal delay, while a flight scheduled at 8:55 a.m. and genuinely over 15 hours late would still roll up to the same calendar day under both dates. In this regime, the timing variance is much better captured as a directly stored **fact** — a delay or lag, computed once during ETL from the actual and scheduled timestamps — than as a second dimension. Where a business process's actual timings genuinely diverge from scheduled ones often enough to matter (project actuals routinely landing weeks after a planned date, say), a separate actual-date role-playing dimension is worth the extra foreign key, since grouping and filtering by the actual calendar period is then a real, distinct question from grouping by the scheduled one. Either way, prefer computing and storing the precise delay/duration as an [additive fact](additive-fact.md) during ETL over leaving BI users to perform date/time arithmetic (especially across time zones) themselves — see the [accumulating snapshot fact table](accumulating-snapshot-fact-table.md)'s lag/duration facts for the general pattern.

## Role-playing and outrigger applications

A fact table frequently references the date dimension more than once for different milestones (order date, ship date, delivery date) — see [role-playing dimension](role-playing-dimension.md). A [fact-specific calendar](fact-specific-calendar.md) is a further role-playing application specific to one fact table: a date-dimension view augmented with that table's own load recency and completeness, used for reliable year-to-date and "last N complete periods" logic — see [year-to-date facts](year-to-date-facts.md). When another dimension needs to filter or group by a secondary date's non-standard calendar attributes (e.g., a store's first-open-date fiscal period), the recommended pattern is a view acting as a second logical copy of the date dimension, an [outrigger dimension](outrigger-dimension.md), with every column distinctly relabeled (e.g., `first_open_day_number`, `first_open_month`) so it can't be confused with the primary date dimension joined to the fact table.

For genuinely different *calendar systems* in a multinational deployment (Gregorian, Hebrew, Islamic, Chinese, and so on), see [multiple fiscal calendars](multiple-fiscal-calendars.md) for the same outrigger technique applied to calendar-system variation rather than fiscal-period variation.
