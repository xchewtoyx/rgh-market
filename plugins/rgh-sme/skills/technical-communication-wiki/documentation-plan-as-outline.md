sources:
  - title: "Docs for Developers: An Engineer's Field Guide to Technical Writing"
    resource: "Docs for Developers (Bhatti, Corleissen, Lambourne, Nunez, Waterhouse), ch. 2"

A documentation plan is a flexible, reviewed outline of the reader's journey through a whole set of documents, built before any individual page is drafted. Its purpose is preventive: without one, teams tend to write whatever page seems most pressing at the moment, which produces documentation that omits information critical to the supported path while over-documenting edge cases that quietly lead readers away from it.

Build the plan from the audience and research artifacts already established (see [the curse of knowledge and audience research](curse-of-knowledge-and-audience-research.md) and [documentation research artifacts](documentation-research-artifacts.md)), plus launch takeaways, feature priority, what readers already know coming in, the use cases actually being supported, and known points of friction. From those inputs, produce a content outline listing every planned page with a title, a [documentation type](choosing-documentation-types.md), and a one-line purpose — deliberately not the prose itself yet.

The single most useful check on a plan at this stage is whether it forms a coherent journey when read straight through as a list of titles and purposes: a gap or an awkward jump at this level usually indicates either a research gap (the writer doesn't yet know what the reader needs there) or a real product problem (the journey is awkward because the product itself is), not just a documentation problem to write around. Getting stakeholder and, where possible, user feedback on the plan before [drafting](drafting-with-outline-first.md) is far cheaper than getting the same feedback on finished prose — the plan is meant to be revised at this stage, before coordinating the actual writing, visuals, publication, and ongoing maintenance against it.
