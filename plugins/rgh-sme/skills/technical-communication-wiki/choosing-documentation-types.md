  Different reader needs call for structurally different kinds of
  documentation — conceptual, procedural, and reference material each
  answer a different question and shouldn't be blended into one page.

Choosing a documentation type is choosing what question a page exists to answer, and mismatching type to need is a common source of documentation that's technically present but not useful. **A document should have one singular purpose and stick to it** — the way a well-scoped API does one thing well. Monolithic pages that mix links, conceptual explanation, and exhaustive reference fail because they serve no single reader job and grow long enough that nobody reads them; when content does not fit the page's purpose, split it rather than append. Code comments explain non-obvious intent, trade-offs, assumptions, or constraints close to the code they describe — they answer "why is this here," not "what does this do," which the code itself already shows. READMEs orient a new contributor and give install, use, and contribution information at the point someone first encounters a codebase. Getting-started material has one job: a fast, confidence-building first success, not comprehensive coverage.

**Conceptual documentation** explains one core idea at a time, and a genuine test of whether a conceptual page succeeds is whether a reader who's read it can explain the idea back in their own words — a page that can't survive that test is probably still a collection of facts rather than an explained concept. It **augments** reference material rather than replacing it; some duplication is acceptable when it buys clarity, and unlike reference docs it need not cover every edge case — sacrificing some strict completeness for understanding is part of the job (see [the completeness-accuracy-clarity tradeoff](completeness-accuracy-clarity-tradeoff.md)). Complex cross-cutting behavior often needs a standalone conceptual page because no single API file comment is the natural home for it.

**Procedural documentation** teaches toward a goal through ordered, single actions, and splits into two distinct sub-types with different jobs. **Tutorials** use a safe learning environment, test data, and non-production exercises to build a skill; if a tutorial exceeds roughly ten steps, either split it or treat the length as a signal that the underlying product may have needless complexity worth raising with engineering. Number [only user interventions](tutorial-step-numbering.md), not invisible system-side work. **How-to guides** solve a real, specific business problem with a short introduction, explicit prerequisites, a tightly focused sequence of steps, and next steps; prerequisites do double duty — they reveal real dependencies, and they function as an escape hatch for a reader who has landed on the wrong page for their actual situation. A how-to guide should stay self-contained; sending a reader on a mid-task detour to another page for something the guide itself could state creates tab-hopping that increases the odds they don't come back.

**Reference documentation** describes cause and effect precisely and exhaustively: API resources, endpoints, methods, parameters, examples, response formats, status codes, and known errors with their fixes. Prefer annotated code and generated references wherever the source can produce them accurately, keeping human-authored procedures for the parts a generator can't capture. In-code reference splits into [API comments versus implementation comments](api-comments-versus-implementation-comments.md); keep generated or header-level reference [single-sourced](single-source-with-pointer-references.md) as much as possible. Function-level comments should be [scan-friendly](scan-friendly-function-comments.md) so seekers can assess relevance quickly.

**Design documents** persuade and record before major work begins: goals, implementation strategy, key decisions with trade-offs, and alternatives considered. They are reviewed like code review before code exists, then serve as historical record and a checkpoint at launch — did the project meet the goals it stated? Design reasoning belongs here, not in API reference.

**Landing pages** route readers to the right next document; see [landing pages as traffic cops](landing-pages-as-traffic-cops.md). A **glossary** establishes one consistent definition per key term across a whole documentation set — inconsistent terminology for the same concept is a recurring, quietly costly failure mode. **Troubleshooting** content should state the issue and the actionable fix together, ordered by frequency or by where in a workflow the issue occurs, and should use the reader's actual, searchable error message as the entry point rather than a paraphrase of it. **Changelogs** record what changed, when, and why for every material change; **release notes** build on a changelog by adding the user-facing impact and any action the reader needs to take as a result.
