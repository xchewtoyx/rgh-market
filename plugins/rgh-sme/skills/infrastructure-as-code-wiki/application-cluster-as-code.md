An application hosting cluster (Kubernetes, AWS ECS, HashiCorp Nomad, Mesos, and similar) dynamically deploys and runs application instances across a pool of servers, separating the concern of orchestrating applications from provisioning and configuring the servers underneath. Like any part of the runtime layer, it should be defined with [infrastructure stack code](infrastructure-stack.md), following the usual [sizing patterns](monolithic-stack-antipattern.md) — starting with a monolithic stack while small, splitting the host-node pool out from cluster management as complexity grows, so each piece can be provisioned and tested independently rather than paying the [blast radius](blast-radius.md) and provisioning time of the whole cluster for every change.

There are two implementation approaches: **cluster as a service**, using a managed offering from the infrastructure platform (EKS, AKS, GKE, ECS), and **packaged cluster distribution**, deploying and managing a cluster solution (via kops, kubeadm, or full distributions like OpenShift) onto infrastructure you provision yourself. A vendor-managed Kubernetes cluster is not, by itself, a cloud-portability abstraction layer — applications still need storage, networking, monitoring, identity, and secrets management, which differ across platforms unless a team builds its own [abstraction layer](abstraction-layer-for-infrastructure.md) on top.

How many clusters to run, and how to share them, is a distinct design decision driven by the same forces as [drawing boundaries between infrastructure components](drawing-boundaries-between-infrastructure-components.md) generally: managing changes safely (at minimum, one cluster for testing changes before production), segregation for governance (isolating regulated workloads like PCI-scoped services onto their own cluster), configurability, performance and scale limits, and availability. Common strategies include one cluster for everything, separate clusters per delivery stage, and separate clusters per team or governance boundary — each trading isolation against operational overhead differently. A [service mesh](service-mesh.md) commonly runs alongside an application cluster to manage connectivity between the application instances it schedules.

Kubernetes clusters schedule containers grouped into **Pods** rather than individually: a Pod is a set of related containers guaranteed to be co-located on the same node, sharing an IP address, port space, and (optionally) ephemeral storage volumes, and allocated or deallocated together as a unit — the point is to cut communication cost between tightly-related containers (a service and its sidecar, most commonly) below what separate scheduling and cross-node networking would cost. A service mesh is typically packaged this way: the mesh sidecar sits in the same Pod as the application container it proxies for. Container images themselves are portable across different vendor runtime engines (Docker, containerd) because the interface between a container and its runtime engine is standardized by the Open Container Initiative — a container built on one complies with the others, though the cluster's own control-plane definitions (manifests, operators) are not similarly standardized and remain the harder part of any inter-cluster portability effort.
