description: The circular problem of untested infrastructure code — you need tests in place before changing it safely, but adding tests often requires changing it first — and the conservative dependency-breaking approach that resolves it.

A large share of real infrastructure code is untested: hand-grown Ansible playbooks, Terraform configs assembled under deadline pressure, CloudFormation templates nobody has touched since the person who wrote them left. Changing any of it safely runs into a circularity — to change the code with confidence, you want [tests](testing-declarative-infrastructure-code.md) or [test fixtures](test-fixtures-for-infrastructure-stacks.md) around it first; but adding those tests often itself requires restructuring the code, which is exactly the risky activity you wanted a safety net for before attempting.

The way out is not to refactor freely and hope, but to make the smallest, most mechanical changes needed to create a seam a test can attach to — nothing more. Concretely: a hardcoded provider credential or account ID that blocks pointing a test at a fixture instead of live infrastructure gets pulled out to a variable; a monolithic module that couples an untestable piece to an easily-testable one gets split just enough to isolate the two, per [drawing boundaries between infrastructure components](drawing-boundaries-between-infrastructure-components.md). These changes are done without the safety net they're meant to create, so they must stay deliberately conservative and mechanical rather than a chance to also improve the design — that's a separate, later step once tests exist to catch a mistake.

This trade-off is worth naming honestly: a dependency-breaking change can leave the code looking locally worse — an extra parameter that only exists to make substitution possible, a split that isn't really about cohesion — purely so it becomes testable. Accept that scar deliberately rather than avoiding it: once tests exist around the seam, later work (ordinary [refactoring](safe-infrastructure-refactoring-with-moved-blocks.md), further decomposition per [extracting resources from a monolithic stack](extracting-resources-from-a-monolithic-stack.md)) can heal it with actual safety-net coverage in place. Treating "no tests yet" as a reason to avoid touching legacy infrastructure at all just leaves the untested area growing; treating it as license to refactor freely risks the exact regression the tests were meant to prevent. The resolution is doing only the minimum, most conservative cut needed to get a first seam under test, then building outward from there. When even that minimal cut isn't affordable right now, [sprouting or wrapping](sprout-and-wrap-for-untested-infrastructure.md) the untested code with new, separately-tested infrastructure is a narrower fallback that makes forward progress without touching the untested area at all.
