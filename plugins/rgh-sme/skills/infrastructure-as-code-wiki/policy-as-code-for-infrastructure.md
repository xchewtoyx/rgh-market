Policy-as-code tools (Open Policy Agent with its Rego language, HashiCorp Sentinel, Checkov, tfsec, Trivy) evaluate machine-readable rules against a plan's structured output before anything is actually applied — for example, exporting `terraform show -json tfplan` and checking every `aws_s3_bucket` resource change for a missing `server_side_encryption_configuration`, failing the pipeline if any bucket would be created unencrypted. Because this runs against the *plan*, it catches violations before any real infrastructure exists, at the cheapest, fastest, and most stable end of an infrastructure test suite — alongside static analysis and linting (`tflint`, `tfsec`, `checkov`), well before anything that requires actually provisioning resources, such as [Terratest](testing-terraform-with-terratest.md). Policy rules are typically written to map directly onto external compliance frameworks (CIS Benchmarks, NIST, PCI-DSS), so a single codified rule can serve both as an engineering guardrail and as evidence for an audit. Static, plan-time scanning like this is usually paired with dynamic scanning of already-running infrastructure (tools such as Falco or Cloud Custodian), which catches drift, unauthorized manual changes, and runtime threats that a plan-time check can't see because they happen after the fact.

This is a concrete implementation of [shift-left governance](governance-in-pipeline-based-workflow.md): instead of a human reviewer manually checking whether a proposed change complies with policy, the policy itself becomes an automated, repeatable check embedded in the pipeline, and a governance specialist's job shifts toward writing and maintaining good policy rules rather than personally reviewing every change. It complements, rather than replaces, [testing declarative infrastructure code](testing-declarative-infrastructure-code.md) more generally — plan-level policy checks catch a specific, valuable class of risk (does this violate a known rule) that's distinct from testing whether the infrastructure actually works once applied.

Not every rule needs to block deployment with equal force; a useful three-tier enforcement hierarchy keeps policy-as-code from becoming an all-or-nothing obstacle: **hard mandatory** rules are non-negotiable and always block the pipeline (an unencrypted S3 bucket, a publicly exposed database); **soft mandatory** rules block by default but allow an explicit, reviewed override for a specific, justified case (opening a public load balancer's port 80/443 to `0.0.0.0/0`); and **advisory** rules surface a warning without blocking anything (recommending a newer TLS cipher suite or a newer base image). Matching a rule's severity to its actual risk keeps hard blocks credible and reserved for genuine non-negotiables, rather than training engineers to routinely bypass an overly strict gate.
