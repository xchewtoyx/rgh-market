---
type: concept
title: "Pattern: Deferred Handler Notification"
description: Deferring a disruptive convergence action, such as a service restart, until the end of a run, and firing it at most once, only if a task that requests it actually reported a change.
sources:
  - title: Ansible for DevOps
    resource: "Ansible for DevOps (Jeff Geerling), ch. 4, ch. 5"
---

Some convergence actions only need to happen as a *side effect* of another change — restarting a service after its config file was rewritten, reloading a daemon after a package upgrade — rather than as an end in themselves, and are disruptive enough (dropped connections, a moment of downtime) that firing one per triggering task, in the middle of a run, is worse than batching them. Declarative [server configuration tools](server-configuration-code.md) address this with a deferred-notification mechanism: a task that changes something relevant declares intent to notify a named handler, and the handler itself only runs — at most once, regardless of how many tasks notified it — after every other task in the run has completed, and only if at least one notifying task actually reported a change.

This matters for two reasons beyond convenience. First, it makes the disruptive action [idempotent](idempotent-infrastructure-code.md) by construction: a rerun where nothing changed notifies nothing, so the service is never restarted for no reason, keeping the run safe to repeat unattended (see [continuous configuration synchronization](continuous-configuration-synchronization-pattern.md)). Second, deferring to end-of-run avoids acting on a not-yet-fully-configured system — restarting a web server the moment its virtual-host file is written, before the certificate or document root referenced by that file has also been put in place, would fail; deferring the restart until the whole convergence run finishes means every prerequisite is already in place by the time the disruptive action actually happens.

The pattern has two sharp edges worth naming explicitly. If the run itself fails partway through, before reaching the point where pending handlers would fire, those handlers are simply never run on that host — silently leaving a config file updated but the service that reads it not yet restarted, unless the tool provides an explicit override (an in-run directive to flush pending handlers immediately, or a run-wide flag to force deferred actions to run despite a failure) to force deferred actions to run anyway. And because a handler only fires once no matter how many tasks notified it, a handler can safely be shared and notified redundantly by many unrelated tasks — this is the mechanism's main practical benefit, letting many small, independent changes converge into a single restart rather than one per change. A notifying task can also target more than one handler at once, and handlers can themselves notify further handlers, chaining a small dependency graph of deferred actions (a restart notifying a second, dependent restart) rather than requiring one flat list.

Deferred notification is a narrower, more automatic sibling of [block/rescue/always error handling](block-rescue-always-error-handling.md): both let a convergence run keep going past something that would otherwise disrupt it, but a handler defers a *guaranteed-safe* follow-up action to the right moment, while block/rescue is for genuinely tolerating a task's outright failure.
