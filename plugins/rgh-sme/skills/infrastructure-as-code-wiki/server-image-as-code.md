A server image is a snapshot built from clean, known sources — never from a live running server — used to create multiple consistent server instances (people sometimes call this a *golden image*). Teams build custom images instead of using platform-provided stock images to satisfy governance requirements, harden for security, optimize performance, preinstall common packages, or bake configuration for a specific server role.

Images can be built **online** (boot a clean instance, configure it, convert it to an image — simple but slow) or **offline** (mount a source image as a disk volume and configure the files directly, often via `chroot` — faster but trickier to get right). Either way, a build combines several origin elements: image builder code (e.g. a Packer template), an origin source image, [server configuration code](server-configuration-code.md) or simple scripts, and other server content.

Images need explicit versioning (embedded in the name or in tags, often combining semantic versioning with a build timestamp) so any running instance can be traced back to the image version it came from — critical for knowing which instances need rebuilding when a vulnerability is patched. New versions can be built by *reheating* the previous image as the source (faster, but risks carrying forward stale leftovers) or *baking fresh* from original sources each time (cleaner and more reliably reproducible). Multiple teams sharing an image need a strategy for rolling out new versions — either flowing automatically through each consuming team's own pipeline, or *pinning* to a known-good version until the consuming team is ready to test and adopt the new one.

Images should be built, tested, and delivered through their own [pipeline](infrastructure-delivery-pipeline.md), ideally rebuilt on a short cadence (weekly rather than every few months) so each rebuild carries fewer changes to test and debug — the same [continuous testing rationale](optimizing-infrastructure-for-continuous-change.md) that applies to any other infrastructure code. How much configuration to push into the image versus apply at server-creation time is the [baking vs frying](baking-vs-frying-server-configuration.md) trade-off; teams managing many role-specific images often layer them (a base OS image feeding role-specific images) to avoid duplicating shared configuration across every image.

Container images are the same idea at a different origin format, and can be built with the same [server configuration code](server-configuration-code.md) used for VMs, in three distinct ways worth distinguishing: running the configuration tool's steps *inside* the container-build process itself (baking the config into the image at build time, analogous to a VM image build, but forgoing the image builder's own native build-layer caching in the process, since the build-layer tool can no longer see the configuration steps as independent, cacheable layers the way it can with its own native build instructions); running the configuration tool *outside* a helper container that applies configuration to it and then commits the result as a new image (getting a genuinely offline-built, cleanly-layered image without embedding the configuration tool or its dependencies inside the shipped image at all); or driving configuration entirely at container run time via a connection mechanism that lets the tool execute inside an already-running container without the tool ever being installed in the image — the container-equivalent of frying, and useful mainly for interactive debugging of running instances rather than repeatable image builds, since it works against [immutable infrastructure](immutable-server-pattern.md)'s general expectation that a running instance is never modified in place.
