Traditional ("Iron Age") disaster recovery treats failure as a rare, special event, tested infrequently — some organizations only test failover once a year or less, on the assumption that the team will improvise a working recovery when it's actually needed, even if it takes days. This tends to optimize for MTBF (Mean Time Between Failure) at the cost of everything else, because preventing change was the only real lever available when infrastructure was physical and slow to rebuild.

Continuous disaster recovery instead reuses the same code and tooling that provisions and changes infrastructure day-to-day to rebuild failed infrastructure — an approach only available once infrastructure is genuinely [reproducible](reproducibility-principle.md). Because the [principle of assuming systems are unreliable](infrastructure-platform-layers.md) means any given instance might be moved, replaced, or destroyed by the platform at any time, being ready to rebuild isn't optional; it's a design requirement, not a rare event to prepare for separately. Treating recovery as an extension of normal operations — the same rebuild-and-reapply mechanisms exercised many times a day as part of ordinary work — makes it far more reliable than treating it as an exception, because a broken rebuild process is far more likely to be caught by a routine pipeline failure than to be discovered only during an actual disaster. This shift favors optimizing for MTTR (Mean Time to Recover) — Cloud Age infrastructure practice is not "move fast and break things," but "move fast and fix things," and per the [four key delivery metrics](four-key-delivery-metrics.md), teams that focus on speed and MTTR tend to get strong MTBF as a side effect rather than by sacrificing speed for it.

**Chaos engineering** — pioneered by Netflix's Chaos Monkey — takes this further by deliberately injecting known, expected failure scenarios into production to prove that detection and recovery mechanisms actually work, rather than assuming they do because they were designed to. It is explicitly not about causing irresponsible outages; it targets specific scenarios the system is expected to already handle, giving fast feedback the moment some other change has silently broken that handling. See [testing infrastructure in production](testing-infrastructure-in-production.md) for how this fits alongside other in-production testing techniques, and [failure scenario mapping](failure-scenario-mapping.md) for how teams decide which scenarios are worth this kind of deliberate exercise. Recovering system *data*, as opposed to stateless infrastructure, needs its own explicit plan — see [data continuity strategies](data-continuity-strategies.md).
