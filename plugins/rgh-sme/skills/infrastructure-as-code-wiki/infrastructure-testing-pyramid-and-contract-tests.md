A useful four-layer vocabulary for infrastructure test suites, refining the general [progressive testing for infrastructure](progressive-testing-for-infrastructure.md) idea into named layers: **unit tests** statically check standalone configuration — naming conventions, resource counts, loop and conditional logic, variable constraints — against the code's AST or a `plan` output, with no live cloud resources involved; **contract tests** statically verify that a module's declared inputs and outputs still match what its callers expect, catching a breaking interface change (an output silently switching from a public IP to a private one, say) in CI before the change is ever applied anywhere; **integration tests** provision real, ephemeral resources into a sandbox to verify actual provisioning mechanics against live cloud APIs — does the VM boot, does it land in the right subnet — then tear down; and **end-to-end tests** validate a full, multi-tier stack's real user-facing behavior in a staging environment, such as an HTTP request actually traversing a load balancer to a backend database.

A contract test is the interface-boundary-specific case of the more general observation, made in [testing declarative infrastructure code](testing-declarative-infrastructure-code.md), that combinations of declarations are often more worth testing than individual declarations — here the "combination" being tested is specifically the handshake between a module's published outputs and what its known consumers expect from them, which is also the same underlying idea behind [consumer-driven contract testing](apply-time-project-integration-pattern.md) at the pipeline level.

Which layers matter most differs by what kind of artifact is under test: shared, reusable **modules** (see [infrastructure module design patterns](infrastructure-module-design-patterns.md)) get the most value from unit, contract, and ephemeral integration tests, since the priority is proving the building block is robust and honors its contract in isolation; **environment configurations** that assemble modules together get more value from integration and end-to-end tests across persistent environments, since the priority there is proving the assembled system actually works end to end. Two supporting disciplines apply across every layer: smoke or sanity tests give a fast post-apply sanity check (a port responds, a health endpoint returns 200) distinct from full functional testing; and pruning flaky, non-deterministic tests is as important as writing new ones, since a test that fails unpredictably trains people to ignore failures rather than investigate them.

A minimal, tool-agnostic checklist for what's worth testing on any reusable server-configuration module, regardless of which of these layers it falls into: does it pass basic syntax/lint validation (the cheapest possible unit-level check, catching malformed code before anything is applied); does it run to completion without failing against a clean target; is it [idempotent](idempotent-infrastructure-code.md) (a second run against the same target reports no further changes); and does it actually do what it claims (a functional check specific to the module — a port answers, a binary is on the `PATH`, an expected file exists). The first three are close to mechanical and apply to nearly any module; the fourth needs module-specific knowledge and is, per this checklist, "the most important part." Dedicated tools exist purely to assert this fourth, functional layer against a converged host, independent of whatever tool applied the configuration — Serverspec and goss are named examples, both agentless and usable locally, over SSH, or against a container. A framework purpose-built for orchestrating a module's whole test matrix (spinning up multiple clean target environments, applying the module, and running assertions against each) is a distinct, higher-level tool in its own right — Molecule is a widely used example for Ansible roles specifically.
